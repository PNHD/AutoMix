# P0-M6-R2 — App-Controlled Continuation Queue

Status date: 2026-08-18

Binding task: `P0-M6-R2 — APP-CONTROLLED CONTINUATION QUEUE`, issued directly by the project owner as a continuation of the same AutoMix / P0-M6 session, on top of the accepted `P0-M6-R1` handoff at commit `b36e8bd347f0f41e7cddc2aebd48d6ea9969ae5d`.

## Binding live conclusion carried forward

The owner's real, multi-run Spotify Premium testing (`P0-M6-R1`) established `SPOTIFY_SINGLE_URI_AUTOPLAY_NOT_AVAILABLE_IN_TESTED_WEB_PLAYBACK_SESSION`: arbitrary single-URI seed playback, Transfer Playback, and seed identity all worked; natural full-song end and a near-end probe both showed Spotify's own Autoplay never supplied a continuation (`next_tracks` stayed empty). Per the task, no further round was spent trying to recover Spotify's native single-URI Autoplay. This round instead builds the app's OWN continuation loop: the app itself selects and queues each successor via the public Web API, so the owner still only ever picks the initial seed.

## Phase A — real API response bug

The live log showed successful Player-API write calls (Transfer Playback, Play, Next, Queue) throwing `Unexpected token ... is not valid JSON`. Root cause: `_api()`'s prior 204-only special case still ran `JSON.parse(text)` unconditionally on any other non-204 response with a non-empty `text` -- and some real successful Player responses arrive as `200` with an empty or plain-text (non-JSON) body, not `204`.

Repaired with a new pure module, `src/adapters/spotify-api-response.js` (`parseSpotifyApiResponse`), that turns every response shape into an explicit branch: `EMPTY_204`, `EMPTY_SUCCESS` (2xx, empty/whitespace body), `JSON` (2xx, valid JSON), `TEXT` (2xx, non-JSON body -- the exact previously-crashing case), `EMPTY_ERROR`, `JSON_ERROR`, `TEXT_ERROR`. Errors are raised as a new `SpotifyApiError` carrying only `method`/`path`/`status`/`body`/`bodyType` -- never a token, header, or full URL with query secrets. `sanitizeErrorText` redacts any `Bearer <token>`-shaped substring and truncates long bodies, as defense-in-depth (no real path today constructs an error body containing a token). `_api()` in `SpotifyPublicControlAdapter.js` now delegates entirely to this module. 30/30 deterministic tests, including an integration case constructing a real adapter with a monkey-patched `fetch` reproducing the exact `200`-with-empty-body live failure.

## Phase B — queue-aware controls

`GET /me/player/queue` (new scope `user-read-playback-state`, the scope Spotify's docs require for this endpoint) is now the single source of truth for "does a real queued successor exist." New pure module `src/adapters/spotify-queue-truth.js` (`deriveQueueTruth`, `isNextControlEnabled`, `nextControlState`, `describePlayAtNaturalEnd`) turns the raw response into a sanitized (opaque-token-only) truth snapshot. `SpotifyPublicControlAdapter.getRealQueueTruth()` polls it and caches `_lastQueueTruth`; `next()` now refuses to call the SDK's `nextTrack()` at all once `_lastQueueTruth` shows no real successor (fails safe, never silently no-ops or surfaces a misleading Spotify error), and the UI disables the Next button + shows `NO_QUEUED_NEXT_TRACK` / `NEXT_TRACK_QUEUED`. `getPlayAtNaturalEndDescription()` makes Play's behavior at natural end with an empty queue truthful (`RESTART_SAME_SEED`, never described as advancing). 33/33 deterministic tests.

## Phase C — public candidate pool

New pure module `src/adapters/spotify-candidate-pool.js`. Sources, in preference order: `GET /me/top/tracks` (new scope `user-top-read`), `GET /me/player/recently-played` (new scope `user-read-recently-played`), and a bounded `GET /search` fallback (existing `limit<=10` clamp) used only when the two affinity sources together are too small (`needsSearchFallback`, threshold 5). The Recommendations endpoint, Audio Features, Audio Analysis, and the deprecated artist-top-tracks endpoint are never called -- enforced both by omission and by a static regression test (`verify_spotify_provider_boundary.mjs`, comment-stripped source grep). `toPlannerCandidate` (`spotify-api-requests.js`) strips every raw track down to id/uri/primary-artist-id/duration/explicit/playability -- no title/name text ever enters planning state. Pool assembly (`assembleCandidatePool`) is deduplicated (first-seen source wins) and bounded to `MAX_CANDIDATE_POOL_SIZE = 60`. 22/22 deterministic tests.

## Phase D — next-track planner v0

New pure module `src/adapters/spotify-planner.js`. Explicitly NOT an acoustic-compatibility model -- it never claims BPM/key/beat/energy/transition-quality compatibility (verified by a test asserting the planner's own output text never mentions those terms). Hard exclusions, evaluated in order: malformed item, missing/invalid track URI, is-current-track, already-played-this-session, recent-repeat-window, unplayable, immediate-same-primary-artist, explicit-content (only when the runtime context requests it), duplicate URI. Ranking priority for the eligible set: user-affinity source (top-tracks > recently-played > search) > not-played-recently (via `recentPlayRank`) > artist diversity (vs. artists already used this AutoMix session) > duration continuity vs. the current track > a final deterministic opaque-token tie-break (never random -- proven by asserting identical results regardless of input array order). The returned `reason` names whichever criterion actually distinguished the winner from the rest of the eligible set, not just its own affinity tier. 30/30 deterministic tests.

## Phase E — one-track lookahead queue

New pure module `src/adapters/spotify-lookahead-queue.js` (`LookaheadQueueController`), plus `buildQueueTrackRequest` (`POST /me/player/queue?uri=...&device_id=...`, query params only, no body -- `spotify-api-requests.js`). Implements the exact required state machine: `SEED_ACTIVE -> NO_SUCCESSOR_QUEUED -> SELECTING_SUCCESSOR -> SUCCESSOR_QUEUE_REQUESTED -> SUCCESSOR_CONFIRMED -> SUCCESSOR_BECOMES_CURRENT -> SELECTING_NEXT_SUCCESSOR` (looping back into a fresh `SELECTING_SUCCESSOR`). Guarantees: never starts a second selection cycle while one is in flight (`ALREADY_IN_PROGRESS`); never re-enqueues a token already successfully queued this session (`DUPLICATE_SKIPPED`); a duplicate `player_state_changed`-derived advance for the same current track is a no-op (`DUPLICATE_EVENT_IGNORED`); a fixed, bounded retry policy (`MAX_QUEUE_REQUEST_ATTEMPTS = 3`) on the queue-write call, falling back to `NO_SUCCESSOR_QUEUED` (never stuck) if all attempts fail; confirmation is a real `GET /me/player/queue` check (Phase B), never assumed. `SpotifyPublicControlAdapter.runLookaheadCycle()`/`confirmLookaheadSuccessor()`/`getLookaheadStatus()` wire this controller to the adapter's own `_api()` (inheriting the Phase A repair) and to real `player_state_changed` events (`_onPlayerStateChanged` now also grows `_sessionPlayedIds`/`_usedArtistIds` and feeds `onTrackAdvanced`). All Phase C/D/E session state resets per seed (`playSeedTrack()`), so nothing leaks across seeds. 47/47 pure-controller tests plus 24/24 real-adapter integration tests (candidate pool -> planner -> queue -> confirm -> real `player_state_changed` advance -> second cycle, driven through the actual `SpotifyPublicControlAdapter` class with a monkey-patched `_api`, not a reimplementation).

## Phase F — live validation UX

New "Real queue truthfulness" status (Next control state, truthful Play-at-natural-end hint) and a new "App-controlled continuation queue" panel (lookahead state, candidate pool size, selected successor token, selection reason, successor confirmed yes/no, refill count, consecutive-automatic-track count) in `index.html`/`app.js`/`styles.css`. A new slower (2s) poll loop, `startLookaheadOrchestration()`, is what actually makes the product flow automatic: it polls real queue truth, and whenever the lookahead controller is idle (no successor queued, or the prior successor just became current), runs one full select-and-queue cycle with no owner interaction required beyond the original seed pick. Verified with a real-browser smoke check (Browser tool, http://127.0.0.1:5500/): the new panel renders, Next starts correctly disabled with `NO_QUEUED_NEXT_TRACK` and the truthful natural-end hint, and switching Spotify Live <-> Local DSP Live modes produces zero console errors in either direction. All existing progress-slider / near-end-probe / seed-epoch / manual-attribution UI is unchanged and reused as-is.

## Unknowns / risks carried into the owner gate

- None of Phase A-F has yet been exercised against the real Spotify API by a human -- every test above is deterministic/synthetic (monkey-patched `_api`/`fetch`), by design (the task explicitly stops before the real three-track owner run). The real owner run is the first point at which `GET /me/top/tracks` / `GET /me/player/recently-played` / `GET /me/player/queue` response shapes are validated against a live account; `deriveQueueTruth`/`candidatesFrom*` are written defensively (tolerate malformed/missing fields) specifically because their exact real-world shape is `UNKNOWN_NEEDS_PROOF` until that run.
- The candidate pool's bounded `GET /search` fallback query is the seed/current track's own primary artist NAME (the only text-bearing signal already available locally); this is a reasonable but untested heuristic for "when top-tracks/recently-played are too thin."
- `RECENT_REPEAT_WINDOW_SIZE = 20` and `MAX_QUEUE_REQUEST_ATTEMPTS = 3` are judgment calls, not owner-specified constants.
- All prior P0-M6-R1 unknowns/risks (manual-action attribution timeout, DJ-partner-access boundary) are unchanged and still open.
