# P0-M2-R1 — Benchmark Pair Catalog (Illustrative)

Status date: 2026-08-11 (repair pass — R2/R7 audit)

Optional companion to `docs/research/P0-M2-AUTOMIX-QUALITY-BENCHMARK-CONTRACT.md` and `docs/research/P0-M2-CORPUS-MANIFEST-SCHEMA.md`. This document specifies **representative pair definitions** in the manifest schema's shape, demonstrating that every required adversarial case type (benchmark contract §4) is concretely constructible. No audio is included or implied to exist yet — every entry below is a specification for a fixture/pair that corpus-production work must still generate, source, and annotate. Fixture generation itself is out of scope for P0-M2-R1 (research/specification only).

All example fixtures use `provenance: SYNTHETIC` because synthetic material is the only way to guarantee `SYNTHETIC_EXACT` ground truth (manifest schema §6), which is required to make these specific adversarial claims falsifiable rather than merely plausible. Real-world (public-domain/CC0/owner-created) material should supplement this catalog once corpus production begins, per the benchmark contract's anti-overfitting requirement (§10) — synthetic-only coverage would itself be a form of overfitting to clean, idealized structure.

## Reading the `Transition class policy` column (R2/R7 repair)

Every pair below now uses the outcome-aware `transition_class_policy` structure (manifest schema §5) instead of the prior fixed `expected_transition_class_set`. Notation used in the tables:

- **`U:`** — `accepted_unconditional`. Choosing this class is always a correct choice for the pair, regardless of execution quality (execution quality is still separately scored by the objective metrics and catastrophic codes).
- **`C:`** — `accepted_conditional`. Choosing this class is correct **only if** the listed Condition-Registry ID(s) (contract §6) are measured-satisfied by the actual execution. This is the direct fix for the original circularity flaw (R2): a genuinely better engine that corrects the adversarial input is scored as having succeeded, not as having picked the wrong class.
- **`R:`** — `rejected`, with a mandatory reason. Only used where the fixture makes the class **structurally** wrong — no achievable condition, or no condition definable at all — never merely because the input looks difficult. Every `R:` entry below states the specific structural reason, per the R7 requirement that `C11` be annotation-grounded rather than inferred from a vague "strong signals" judgment.

Where a pair has no `R:` line, every non-listed class defaults to rejected under the manifest schema's closed-world rule (schema §5) but carries only the generic "not enumerated as acceptable for this pair" reason, which is intentionally weak and — per contract §9's `C11` definition — is **not**, by itself, sufficient grounding for a `C11` finding without also being explicitly authored with a specific reason. `C11` findings in practice should be expected only on pairs that have an explicit, specific `R:` reason recorded, which is why every catalog pair below that is meant to probe `C11` (the Lane E adversarial subset, §5 below) has an explicit `R:` line.

## Coverage summary against benchmark contract §4/§10/§9 (updated for the R2/R7 repair)

- Every case type named in the benchmark contract's Lane A–E tables (§4.1–§4.5) has at least one concrete `pair_id` above.
- All 31 entries were individually audited for the R2 circularity flaw. Of the 31, **10 pairs retain an explicit `R:` (rejected) entry** (`A-007`, `A-008`, `A-010`, `B-001`, `B-002`, `D-008`, `E-004`, `E-005`, `E-006`, `E-007`); every one of them states a **structural** reason (no signal to align to, no defined cross-meter condition, a class's own duration character being incompatible with the safety condition, an outer-bound comparison against SimpMusic's own shipped ceiling, or a collision provably unavoidable by cue-point choice) rather than "the input looks adversarial." The remaining 21 pairs either always allow the full range of classes (positive controls) or make `FULL_DJ_BLEND` conditionally available on a named, measurable condition — this is the direct, auditable fix for the R2 finding on `A-001`/`A-002`/`A-003`.
- `PAIR-SYN-E-007` and `PAIR-SYN-E-006` remain the two highest-priority pairs for validating the confidence/fallback lane specifically, since they are the direct adversarial tests of `C11_FORCED_WRONG_TRANSITION_STYLE` (contract §9) and of the exact "static global setting, no per-pair fallback" gap P0-M1 documents for SimpMusic — both now carry explicit, structurally-grounded `R:` reasons per R7, rather than being scored against an implicit/undefined notion of what "looks wrong."
- All 31 entries above are `provenance: SYNTHETIC` by design (§ preamble); genre/style tag diversity (pop, hip-hop, rock, etc., per benchmark contract §10) and non-synthetic sourcing are **not yet represented** — this is flagged explicitly as required future corpus-production work, not claimed as already satisfied by this illustrative catalog. The contract's minimum corpus plan (60 Tier-1 pairs, contract §11) requires roughly double this catalog's current pair count per lane on average (this catalog is illustrative/representative, not the full required corpus).
- None of these entries are wired into `manifest.json`/`tier1_fixtures.jsonl`/`tier1_pairs.jsonl` yet (`docs/research/P0-M2-CORPUS-MANIFEST-SCHEMA.md` §1) — that wiring, plus actual audio generation and annotation, is corpus-production work for a future task, explicitly allowed under disposable P0-M3 benchmark-execution prototyping per the benchmark contract's R8 clarification (contract §2/§11), while the shipping production engine remains gated behind the P1 gate (contract §11).
