## Blocker 1 — double-poll confirmation race

The PM reproduced this directly: `runLookaheadCycle()` polled queue truth once to decide what to do, then, for the "awaiting confirmation" branch, called the OLD async `confirmSuccessor()` -- which polled `GET /me/player/queue` a SECOND time internally. Between those two polls, Spotify could legitimately advance the pending successor to `current`, so poll #2 would see an EMPTY queue (the item was consumed, not "never visible") and wrongly report `NOT_YET_VISIBLE_IN_QUEUE` -- permanently stuck in `SUCCESSOR_QUEUE_REQUESTED`, since the later `player_state_changed` for that exact track can only advance an already-`SUCCESSOR_CONFIRMED` controller.

Fixed architecturally: `LookaheadQueueController` gained a PURE method, `confirmSuccessorFromTokens(tokens)` -- takes an already-fetched token array, performs zero I/O, and makes the confirm/not-yet-visible decision synchronously. `SpotifyPublicControlAdapter.runLookaheadCycle()` now polls `getRealQueueTruth()` EXACTLY ONCE per cycle and uses that one snapshot for every decision in that cycle: when awaiting confirmation, `KNOWN_NONEMPTY` calls `confirmSuccessorFromTokens(queueTruth.tokens)` directly (zero additional GETs), `UNKNOWN_API_ERROR` returns `QUEUE_STATE_UNKNOWN_CANNOT_CONFIRM` and stays `SUCCESSOR_QUEUE_REQUESTED` (never reinterpreted as not-yet-visible), and `KNOWN_EMPTY` returns `NOT_YET_VISIBLE_IN_QUEUE` truthfully. A related bug found in the same review: once `SUCCESSOR_CONFIRMED`, the confirmed token legitimately still sitting in the real queue (before Spotify actually advances to it) was being misreported as `EXTERNAL_QUEUE_OCCUPIED` -- fixed with an explicit `SUCCESSOR_CONFIRMED` branch that returns the truthful `AWAITING_CONFIRMED_SUCCESSOR_PLAYBACK` with zero POSTs, never touching the external-occupancy logic. `app.js`'s orchestration loop was simplified to call `adapter.runLookaheadCycle()` as the SINGLE entry point per tick (removing the parallel `getRealQueueTruth()` + `confirmLookaheadSuccessor()` path that was itself contributing extra polls beyond the adapter's own). The old async `confirmSuccessor()` (which still does its own fetch) is kept only for standalone/manual use, explicitly documented as NOT for the orchestration path.

30/30 tests (`verify_spotify_confirmation_race.mjs`): pure `confirmSuccessorFromTokens` proven to perform zero I/O in both the confirm and reject cases; the PM's full 11-step race scenario (seed active -> queue SUCC -> `SUCCESSOR_QUEUE_REQUESTED` -> next cycle confirms from ONE poll -> exactly one `GET /me/player/queue` counted -> `player_state_changed` advances -> `SELECTING_NEXT_SUCCESSOR` -> `consecutiveAutoTrackCount` 2 -> `refillCount` 1); a mechanical reproduction that FORBIDS any second GET during one confirmation decision (throws if attempted) and proves the state machine still advances correctly; an API-error-during-confirmation test proving the exact result `QUEUE_STATE_UNKNOWN_CANNOT_CONFIRM`, that the controller remains `SUCCESSOR_QUEUE_REQUESTED`, zero POSTs, and that it is NEVER `NOT_YET_VISIBLE_IN_QUEUE`; a 20-tick simulation proving no duplicate POSTs (exactly 2, one per successor), no unbounded GET amplification, and no stuck state after a confirmed successor becomes current.

## Blocker 2 — finish privacy repair in app.js

The adapter's own diagnostics were already sanitized (repair pass 1, Blocker 7), but `app.js` itself still built two debug log lines directly from raw owner data: `` `searchTracks("${query}") -> ...` `` (the owner's raw search text) and `` `playSeedTrack(${track.uri}) -> ... {"uris":["${track.uri}"]}` `` (the raw `spotify:track:<id>` URI). Fixed: `searchTracks()`'s log now reads only `` `searchTracks() -> ${results.length} result(s)` ``; `playSeedTrack()`'s log now uses `sanitizeTrackToken(track.uri)` (imported from `spotify-autoplay.js`, the same opaque-token primitive the adapter itself uses) to log `` `playSeedTrack(${seedToken}) -> request accepted` `` instead. The ephemeral search-RESULTS LIST rendered in the DOM (song name/artist as plain `<span>` text) is unchanged and still shows that information, because the owner needs it to pick a song -- that is UI, not tracked/logged evidence, exactly the same distinction already established for the adapter's own snapshots.

11/11 tests (`verify_spotify_app_debug_privacy.mjs`), static source analysis (comment-stripped, same technique as `verify_spotify_provider_boundary.mjs`): proves the exact substrings `${query}` and `${track.uri}` do not appear anywhere in `app.js` at all (since `${...}` interpolation syntax only has meaning inside a template literal, their absence is precise, sufficient proof no template literal anywhere embeds either raw value); positively confirms the repaired log lines exist in the expected opaque-token/count-only shape; a self-test proving the detection logic itself would catch a deliberately-reintroduced bad line; confirms the legitimate name/artist UI list still exists (proving the fix didn't remove the owner-facing feature).

## Package/handoff repair

The PM found the tracked `HANDOFF_TO_PM.md` design itself flawed: it referred to "git log is authoritative" for the exact final HEAD instead of stating it directly, and claimed a ZIP SHA-256 was "recorded below" when none actually was -- a self-referential design (a file trying to record the hash of the ZIP it is itself packaged inside of) that can't actually work without either a stale value or a rebuild-just-to-update-the-hash loop.

Fixed by separating concerns entirely: `HANDOFF_TO_PM.md` (tracked, committed with the code) now only describes the WORK -- what changed, why, and the exact implementation commit SHA (a fact known at commit time, no self-reference) -- and explicitly defers the "exact final pushed HEAD" and ZIP verification hash to a new **untracked** `PM_FINAL_STATE.md`, generated fresh AFTER the push (so it can state the real final HEAD as a plain fact) and included directly in the ZIP. The ZIP's SHA-256 is computed AFTER building it and reported directly in the session's final chat response -- never written back into any file inside the ZIP, avoiding the self-referential rebuild loop entirely.
