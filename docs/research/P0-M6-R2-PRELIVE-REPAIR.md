Status date: 2026-08-18

Binding task: `P0-M6-R2-PRELIVE-REPAIR-REQUIRED`, the PM's independent review of `P0-M6-R2-PM-REVIEW.zip` (commit `faa4e4d`). The PM reran all 382 existing checks (382/382 PASS) and then filed 7 blockers plus a packaging defect before authorizing the real 3-track owner run. This document records the repair; `P0-M6-R2-APP-CONTROLLED-CONTINUATION-QUEUE.md` (prior round) still describes the original Phase A-F implementation this repairs.

## Blocker 1 — scope-aware reauthorization

A token issued before this round's three new scopes (`user-read-playback-state`, `user-top-read`, `user-read-recently-played`) existed could be silently reused, hitting the new endpoints with 403s the owner would never understand. New pure module `src/adapters/spotify-scope.js` (`hasAllRequiredScopes`, `missingScopes`, `parseScopeString`). The stored token now carries a `scope` array (captured from `exchangeCodeForToken`'s response, preserved across a refresh response that omits `scope` -- Spotify's documented behavior when it hasn't changed). `connect()` checks `hasAllRequiredScopes(this._token.scope, SPOTIFY_SCOPES)` before ever using a stored token; on failure it discards ONLY the token (`_discardStaleToken()`, new method) -- the Client ID is never touched -- and returns `SPOTIFY_REAUTH_REQUIRED_FOR_NEW_SCOPES`. `app.js`'s Connect handler routes that reason through `beginLogin()` automatically, so the owner's only required action is clicking Connect again -- no DevTools, no manual localStorage clearing. 22/22 tests (`verify_spotify_scope_migration.mjs`), including a real in-memory `localStorage` shim so the actual `_loadStoredToken`/`_storeToken`/`_discardStaleToken`/`_clientId` code paths run unmodified, not a re-implementation.

## Blocker 2 — tri-state queue truth

`getRealQueueTruth()` collapsed every failure mode (a genuinely empty queue, and any 401/403/429/5xx/network error) into the same "empty" result -- unsafe once queue injection depends on that value (Blocker 3). `spotify-queue-truth.js` was rewritten around an explicit `QueueTruthState`: `KNOWN_EMPTY`, `KNOWN_NONEMPTY`, `UNKNOWN_NOT_POLLED` (the adapter's real initial value now, never `null`), `UNKNOWN_API_ERROR` (carries sanitized diagnostics only: endpoint path with the query string already stripped, HTTP status, `bodyType`, and a sanitized Spotify error message via the new `extractSanitizedSpotifyErrorMessage` -- never a token/URI/device id). `isNextControlEnabled` is true ONLY for `KNOWN_NONEMPTY`; `canInjectToQueue` (new) is true ONLY for `KNOWN_EMPTY`; `nextControlState`/`describePlayAtNaturalEnd` give each state its own truthful label instead of flattening EMPTY and UNKNOWN together. `next()`'s own defense-in-depth gate was adapted to the tri-state value (permissive only before the very first poll, to preserve the pre-existing R1 manual-Next attribution test suites that never populate queue truth -- the owner-facing Next BUTTON is separately, unconditionally disabled for EMPTY or either UNKNOWN state via the UI wrapper methods, which is the actual "Next disabled for EMPTY or UNKNOWN" requirement). 46/46 tests (`verify_spotify_queue_truth.mjs`, fully rewritten).

## Blocker 3 — exactly one-track lookahead, gated on real queue truth

`runLookaheadCycle()` is now a single safe-to-call-every-tick entry point: it polls real queue truth FIRST, always. If the controller is already `SUCCESSOR_QUEUE_REQUESTED` (awaiting confirmation of OUR OWN prior request), this tick's only job is to try confirming it -- never a second selection cycle, regardless of what the real queue shows. Otherwise, a NEW selection/enqueue cycle is attempted ONLY when the real queue is `KNOWN_EMPTY` (`canInjectToQueue`); a `KNOWN_NONEMPTY` queue that isn't ours yields `EXTERNAL_QUEUE_OCCUPIED` with zero POSTs, and any `UNKNOWN_*` state yields `QUEUE_STATE_UNKNOWN_CANNOT_INJECT` with zero POSTs. 13/13 dedicated tests (`verify_spotify_one_lookahead.mjs`) plus reinforcing coverage in the adapter integration suite (a real `player_state_changed`-driven confirm/advance/second-cycle run, and a 10-duplicate-tick simulation proving exactly one POST total).

## Blocker 4 — bounded retry across orchestration ticks

`LookaheadQueueController` already bounded retries WITHIN one selection cycle (`MAX_QUEUE_REQUEST_ATTEMPTS = 3`); nothing previously stopped the ~2s orchestration loop from starting a brand-new cycle against the exact same failing candidate/endpoint forever. New pure module `src/adapters/spotify-queue-error-policy.js` (`classifyQueueFailure`, `isBlockerActive`) classifies a failed cycle's terminal error by HTTP status: `401`/`403` -> `TERMINAL_AUTH_BLOCKER` (systemic, never auto-clears -- requires a real fix, not a retry); `429` -> `COOLDOWN` honoring a real `Retry-After` header when present (now captured on `SpotifyApiError.retryAfterSec`, read from the response header in `_api()`), else a default bound; `404` -> `CANDIDATE_FAILED` (this ONE track can't be queued -- excluded from the planner via a new `PERMANENTLY_FAILED_THIS_SESSION` hard-exclusion reason, no cooldown, a different candidate is tried the very next tick); anything else (5xx, network) -> `COOLDOWN` with the default transient bound. `runLookaheadCycle()` checks `isBlockerActive(this._queueBlocker, Date.now())` before ever attempting a new cycle. 35/35 tests (`verify_spotify_bounded_retry.mjs`), including a 20-tick simulation against a permanently-failing endpoint proving exactly 3 total POSTs (the one bounded cycle), not 60.

## Blocker 5 — real recent-listening exclusion

`recentRepeatWindowIds` was being populated from `_sessionPlayedIds` -- duplicating `ALREADY_PLAYED_THIS_SESSION` instead of reflecting the account's actual real listening history. `_fetchCandidatePool()` now captures `_lastRecentlyPlayedIds` from the real `GET /me/player/recently-played` response (most-recent-first, matching Spotify's own ordering), and `runLookaheadCycle()` feeds the first fixed `RECENT_REPEAT_WINDOW_SIZE` (20) of THAT into the planner -- a genuinely separate exclusion from session history. Separately, `assembleCandidatePool` (`spotify-candidate-pool.js`) was silently dropping a later source's `recentPlayRank` whenever a track already existed in the pool from an earlier source -- meaning a track that was BOTH a Top Track AND recently played lost its recency signal entirely and could rank as if never recently played. Repaired to merge `recentPlayRank` into the kept (first-seen-source) entry instead of discarding the duplicate outright, so a just-played top track is correctly deprioritized against an older, equally-affine one. 16/16 tests (`verify_spotify_recent_history.mjs`).

## Blocker 6 — AutoMix OFF actually stops queueing

`SpotifyPublicControlAdapter.setAutoMixEnabled()` was a no-op inherited from a different (Local-DSP-oriented) capability check. It's now real: `_autoMixEnabled` (default ON, matching the UI's default toggle state) is checked in `runLookaheadCycle()`'s NEW-selection path only -- OFF returns `AUTOMIX_DISABLED` with zero POSTs, but never blocks confirming an item ALREADY queued before the toggle (the public Spotify API has no reliable "remove from queue" endpoint, so this never pretends to have un-queued something). ON simply clears the gate; the next tick resumes normally once real queue truth permits it. 17/17 tests (`verify_spotify_automix_toggle.mjs`), including a regression check that `LocalDSPPlaybackAdapter.js` (a separate class/capability) was untouched.

## Blocker 7 — privacy-safe error/debug output

Two real leaks were found: (1) `_api()`'s thrown `SpotifyApiError` stored the FULL request path VERBATIM, including query strings -- and the queue-injection/seed-play endpoints put a raw track URI and/or `device_id` directly in the query string, so any place that logged/emitted the error (the debug panel, `queue_truth_poll_failed`, etc.) leaked a raw identifier despite the code's own prior claim that it never did. Fixed by stripping the query string in `_api()` before constructing the error. (2) `device_ready`/`device_activated` events emitted the raw Spotify Connect `device_id` directly. Fixed with a new shared primitive, `src/adapters/spotify-privacy.js` (`fnv1aHex`, `sanitizeDeviceToken`) -- `spotify-autoplay.js`'s `sanitizeTrackToken` now delegates to the same hash function (identical output, no behavior change) so track and device identifiers are sanitized through one shared implementation. The raw `device_id` is now kept only on `_deviceId` (for making real API calls); everything emitted uses `_deviceToken` (`DEV_`-prefixed, opaque). `SpotifyApiError` also gained `retryAfterSec` (captured from a `Retry-After` response header, supporting Blocker 4). 19/19 tests (`verify_spotify_privacy_diagnostics.mjs`).

## Packaging defect — stale HANDOFF_TO_PM.md

The prior round's PM ZIP was built BEFORE `HANDOFF_TO_PM.md` was rewritten for that round, so it packaged the still-live-on-disk P0-M6-R1 content by mistake. This round's build order was corrected: the final `HANDOFF_TO_PM.md` content is written FIRST, then the ZIP is built (grabbing that already-correct working-tree file), then `HANDOFF_TO_PM.md` is committed as the final docs commit -- reproducing the same content the ZIP already contains, not a different one.

## Unknowns / risks carried into the owner gate

- Still none of this repair pass has been exercised against the real Spotify API by a human -- every test is deterministic/synthetic, by design (the task explicitly stops before the real owner run). The real 401/403/429/404 response SHAPES from `POST /me/player/queue` are `UNKNOWN_NEEDS_PROOF` until that run; the classification logic is written against Spotify's documented status codes, not an observed real error.
- `RECENT_REPEAT_WINDOW_SIZE` (20), `MAX_QUEUE_REQUEST_ATTEMPTS` (3), `DEFAULT_TRANSIENT_COOLDOWN_MS`/`DEFAULT_RATE_LIMIT_COOLDOWN_MS` (30s) remain judgment calls, not owner-specified constants.
- All P0-M6-R1 and prior P0-M6-R2 unknowns/risks are unchanged and still open.
